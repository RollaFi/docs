title: 'Get Transaction'
openapi: 'GET /wallet/transaction/{transactionId}'
---

Retrieve the full details of a specific wallet transaction, by **either** Rolla's transaction ID **or** the `externalReference` you set when you created it.

## Example Request

```bash
curl -X GET "https://api.rolla.xyz/api/v1/external/wallet/transaction/a1b2c3d4-e5f6-7890-abcd-ef1234567890" \
  -H "X-API-Key: your_api_key_here"
```

## Example Response

```json
{
  "status": 200,
  "success": true,
  "message": "Transaction retrieved successfully",
  "data": {
    "transaction": {
      "id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
      "transaction_type": "withdrawal",
      "status": "completed",
      "description": "Vendor payment",
      "external_reference": "ref-abc123",
      "fee_amount": "53.00",
      "source_amount": "500000.00",
      "destination_amount": null,
      "source_currency": "NGN",
      "destination_currency": null,
      "exchange_rate": null,
      "created_at": "2024-01-15T10:30:00.000Z",

        "account_name": "JOHN DOE",
        "bank_name": "Access Bank",

        "account_number": "0123456789"
      }
    }
  }
}
```

## Looking one up by your own reference

The path segment accepts two things, and Rolla picks by shape:

| What you pass | What it matches |
|---------------|-----------------|
| A UUID | Rolla's transaction `id` |
| Anything else | The `external_reference` on the transaction — the `externalReference` you sent when creating the payout, transfer or swap |

So if you kept only your own reference, you can read the transaction back without ever storing our ID:

```bash
curl -X GET "https://api.rolla.xyz/api/v1/external/wallet/transaction/invoice-8842" \
  -H "X-API-Key: your_api_key_here"
```

<Note>
  An `external_reference` is only unique within the account that set it. If the same reference exists on more than one transaction in scope, the most recent one is returned. Pass the transaction `id` when you need an exact, single row — for example when reconciling.
</Note>

<Note>
  Transaction IDs and references both come back from the [`/wallet/transactions`](/api-reference/endpoint/wallet/transactions) and [`/accounts/transactions`](/api-reference/endpoint/accounts/list-transactions) list endpoints, and from every [webhook payload](/api-reference/webhooks/payloads).
</Note>

## What you can read

The lookup is scoped to what your key can see:

- **An ordinary key** reads transactions belonging to its own business.
- **A partner (white-label tenant) key** reads any transaction across its whole tenancy — its own account and every account it has onboarded. A row you found in [List Transactions Across Accounts](/api-reference/endpoint/accounts/list-transactions) is fetchable by ID here directly; you do **not** need to work out which account owns it first.
- Adding the [`X-Account-Id`](/api-reference/introduction#acting-on-a-tenant-account-x-account-id) header narrows the lookup to that one account, as it does on every other endpoint.

A transaction that doesn't exist and one that belongs to somebody else both return the same `404`, so IDs can't be probed:

```json
{
  "status": 404,
  "success": false,
  "message": "Transaction not found: a1b2c3d4-e5f6-7890-abcd-ef1234567890"
}
```

## Payment tracking references

A cross-border payout carries `uetr` and `tracking_codes` once the SWIFT network returns
them — the references a beneficiary's bank is chased with.

```json
{
  "id": "9a56d01f-dc72-4ace-bbbc-a237bdb1c599",
  "transaction_type": "withdrawal",
  "status": "sent",
  "uetr": "97ed4827-7b6f-4491-a06f-b548d5a7512d",
  "tracking_codes": {
    "UETR": "97ed4827-7b6f-4491-a06f-b548d5a7512d",
    "IMAD": "20260818B1QGC01C000123"
  }
}
```

| Field | Description |
|-------|-------------|
| `uetr` | The payout's **UETR** (Unique End-to-end Transaction Reference) — the UUID that identifies the payment across every bank that touches it. Quote it when tracing or recalling a payment. |
| `tracking_codes` | Every reference recorded against the payout, keyed by name — the `UETR`, plus `IMAD` on corridors that produce one. Read `uetr` for the UETR; use this if you also surface the others. |

<Warning>
  **Both fields are omitted until the reference exists** — they are not returned as
  `null`. The UETR is assigned by the correspondent network *after* the payout is sent,
  typically within minutes but sometimes hours later, so a payout read back immediately
  after you create it will not carry one. Local-rail and stablecoin payouts never get one.
  Branch on the field's presence; never block your flow waiting for it.
</Warning>

<Tip>
  To be told the moment a UETR lands rather than polling for it, subscribe to the
  [`transaction.uetr.assigned`](/api-reference/webhooks/events#payout-tracking-events)
  webhook. It carries the same value.
</Tip>
